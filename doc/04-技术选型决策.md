### 2.2 P2P网络方案

#### 🎯 决策问题

#### 📊 候选方案对比

| 方案 | 优势 | 劣势 | 综合评分 |
|------|------|------|---------|
| **WebRTC** | • NAT穿透成功率高(80-90%)<br>• Flutter插件成熟<br>• 免费STUN服务器<br>• 开发成本低 | • 需要信令服务器<br>• 复杂网络需TURN | ⭐⭐⭐⭐⭐ |

**WebRTC**

4. **开发效率**: 有完整示例代码

#### 🏗️ 技术架构
```
客户端A ←→ 信令服务器(WebSocket) ←→ 客户端B
    ↓                                    ↓
    └────────── WebRTC P2P连接 ──────────┘
              (STUN/TURN辅助)
```

**Hive**（键值存储）:

#### 🗄️ 数据库Schema设计（SQLite）

```sql
-- 宠物表

    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL COMMENT '宠物名称',
    type TEXT NOT NULL COMMENT '宠物类型',
    personality TEXT NOT NULL COMMENT '性格模板',
    created_at DATETIME NOT NULL COMMENT '创建时间',
    updated_at DATETIME NOT NULL COMMENT '更新时间',
    is_active INTEGER DEFAULT 1 COMMENT '是否激活'
);

-- 宠物状态表
CREATE TABLE pet_states (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    pet_id INTEGER NOT NULL COMMENT '宠物ID',

    position_y REAL DEFAULT 0 COMMENT 'Y坐标',

-- 互动记录表
CREATE TABLE interactions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    pet_id INTEGER NOT NULL COMMENT '宠物ID',
    interaction_type TEXT NOT NULL COMMENT '互动类型',
    content TEXT COMMENT '互动内容',
    created_at DATETIME NOT NULL COMMENT '创建时间'
```

#### 决策2: P2P网络方案（2026-05-30）

**决策结果**: 
- **方案**: libp2p + 固定公网中继节点（混合架构）
- **连接策略**: 先连中继，后台升级直连

**架构设计**:

```
┌─────────────────────────────────────────────────┐
│           libp2p混合P2P网络                      │
├─────────────────────────────────────────────────┤
│                                                 │
│  用户节点A (NAT后)                               │
│      ↓                                          │
│      ├─ 立即连接固定中继节点 (1秒) → 用户可用    │
│      │                                          │
│      └─ 后台并行尝试:                            │
│          ├─ 直连用户节点B (2秒)                  │
│          ├─ Hole Punching (3秒)                │
│          └─ 成功后自动升级连接 (DCUtR)           │
│                                                 │
│  固定中继节点部署:                               │
│      ├─ 节点1: 北京电信 (2核4G 5Mbps)           │
│      ├─ 节点2: 上海联通 (2核4G 5Mbps)           │
│      └─ 节点3: 广州移动 (2核4G 5Mbps)           │
│                                                 │
└─────────────────────────────────────────────────┘
```

**连接流程优化**:

1. **立即连接阶段**（用户感知延迟: 1秒）
   - 新节点上线 → 立即连接最近的固定中继节点
   - 通过中继建立通信通道
   - 用户可以开始互动（宠物传送、对话等）

2. **后台升级阶段**（用户无感知）
   - 并行尝试直连（Direct Connection）
   - 并行尝试打洞（Hole Punching）
   - 通过DHT发现其他可用中继节点（其他用户）
   - 成功后使用DCUtR协议自动升级连接

3. **连接优先级**
   - 直连 > 打洞 > 用户中继 > 固定中继
   - 自动选择延迟最低的路径

**技术优势**:

1. **用户体验**
   - 首次连接仅需1秒（比WebRTC的3秒更快）
   - 连接升级过程用户无感知
   - 70%的连接最终会升级到直连

2. **成本效益**（中国网络环境）
   - 初期成本: ¥1,800/年（3个固定节点）
   - 规模效应: 用户越多，互相中继占比越高
   - 5000用户: ¥3,500/年（vs WebRTC的¥5,000）
   - 10000用户: ¥7,000/年（vs WebRTC的¥15,000）

3. **网络性能**
   - NAT穿透成功率: 90-95%（中国环境）
   - 直连成功率: 70%（电信/联通用户）
   - 中继备份: 固定节点 + 用户节点双重保障

4. **可扩展性**
   - 用户规模增长时，可动态增加固定节点
   - 用户互相中继形成网络效应
   - 带宽成本增长远低于用户增长

**固定中继节点配置**:

| 节点 | 位置 | 运营商 | 配置 | 成本/年 | 用途 |
|------|------|--------|------|---------|------|
| 节点1 | 北京 | 电信 | 2核4G 5Mbps | ¥600 | 服务北方电信用户 |
| 节点2 | 上海 | 联通 | 2核4G 5Mbps | ¥600 | 服务华东联通用户 |
| 节点3 | 广州 | 移动 | 2核4G 5Mbps | ¥600 | 服务南方移动用户 |

**总成本**: ¥1,800/年（初期）

**技术实现要点**:

1. **libp2p核心组件**
   - Transport: TCP + WebSocket + QUIC
   - NAT穿透: AutoNAT + Hole Punching
   - 中继协议: Circuit Relay v2
   - 连接升级: DCUtR (Direct Connection Upgrade through Relay)
   - 节点发现: mDNS (本地) + DHT (广域)

2. **Tauri集成**
   - 使用rust-libp2p库
   - 通过Tauri Command暴露P2P接口给前端
   - 实现连接状态监听和事件通知

3. **连接管理**
   - 维护固定中继节点列表（硬编码 + 配置文件）
   - 实现连接池管理
   - 自动重连机制
   - 连接质量监控（延迟、丢包率）

**风险与应对**:

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 开发周期延长 | MVP延迟1-2个月 | 提前规划，分阶段实现 |
| 固定节点故障 | 部分用户连接失败 | 多节点冗余，自动切换 |
| 调试困难 | 开发效率降低 | 完善日志系统，使用libp2p调试工具 |
| 首次集成复杂 | 学习曲线陡峭 | 参考rust-libp2p示例，社区支持 |

**决策理由**:

1. **性能优先**: 1秒连接速度优于WebRTC的3秒
2. **成本考虑**: 用户规模>5000时成本优势明显
3. **可扩展性**: 网络效应使成本增长远低于用户增长
4. **去中心化**: 符合项目理念，用户互相帮助
5. **中国网络适配**: 固定节点覆盖三大运营商，成功率90-95%

**下一步行动**:

1. 搭建3个固定中继节点（北京电信、上海联通、广州移动）
2. 实现libp2p基础框架（Transport + Relay）
3. 实现连接优化策略（先中继，后升级）
4. 测试NAT穿透成功率
5. 实现连接监控和自动切换

```typescript
// src/lib/storage.ts
import { openDB, DBSchema, IDBPDatabase } from 'idb';

interface CyberPetDB extends DBSchema {
    app_config: {
        key: string;
        value: any;
    };
    ai_config: {
        key: string;
        value: {
            provider: string;
            model: string;
            apiKey: string; // 加密存储
            baseUrl?: string;
        };
    };
    ai_cache: {
        key: string;
        value: {
            key: string;
            response: string;
            expireAt: number;
        };
        indexes: { 'expireAt': number };
    };
}

class Storage {
    private db: IDBPDatabase<CyberPetDB>;
    
    async init() {
        this.db = await openDB<CyberPetDB>('cyber-pet', 1, {
            upgrade(db) {
                db.createObjectStore('app_config');
                db.createObjectStore('ai_config');
                const aiCache = db.createObjectStore('ai_cache', { keyPath: 'key' });
                aiCache.createIndex('expireAt', 'expireAt');
            },
        });
    }
    
    // 配置管理
    async getConfig(key: string): Promise<any> {
        return await this.db.get('app_config', key);
    }
    
    async setConfig(key: string, value: any): Promise<void> {
        await this.db.put('app_config', value, key);
    }
    
    // AI缓存（带过期）
    async getCachedAIResponse(prompt: string): Promise<string | null> {
        const key = hashPrompt(prompt);
        const cached = await this.db.get('ai_cache', key);
        
        if (cached && cached.expireAt > Date.now()) {
            return cached.response;
        }
        
        return null;
    }
    
    async cacheAIResponse(prompt: string, response: string, ttl: number = 3600000) {
        const key = hashPrompt(prompt);
        await this.db.put('ai_cache', {
            key,
            response,
            expireAt: Date.now() + ttl,
        });
    }
    
    // 清理过期缓存
    async cleanExpiredCache() {
        const tx = this.db.transaction('ai_cache', 'readwrite');
        const index = tx.store.index('expireAt');
        
        for await (const cursor of index.iterate()) {
            if (cursor.value.expireAt < Date.now()) {
                cursor.delete();
            }
        }
    }
}

export const storage = new Storage();
```

```typescript
    const encrypted = await storage.getConfig(key);
```

```typescript
    };

async function importData(file: File) {
    const backup = JSON.parse(await file.text());
    
    // 1. 恢复SQLite
    await invoke('import_database', { data: backup.sqlite });
    
    // 2. 恢复IndexedDB
    for (const [store, data] of Object.entries(backup.indexeddb)) {
        await importStore(store, data);
    }
}
```

**决策理由**:

1. **性能优化**: IndexedDB处理频繁读写比SQLite快10倍
2. **数据分离**: 结构化数据和配置数据分开存储，职责清晰
3. **浏览器原生**: IndexedDB是浏览器标准API，无需额外依赖
4. **无大小限制**: IndexedDB无5MB限制（LocalStorage有）
5. **事务支持**: 两者都支持事务，保证数据一致性
