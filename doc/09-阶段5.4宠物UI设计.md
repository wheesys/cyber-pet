# 阶段5.4 宠物UI 设计文档

**文档版本**: v1.0
**创建日期**: 2026-05-31
**所属阶段**: 阶段5.4 宠物UI（MVP - 宠物系统）

---

## 1. 背景与目标

阶段 5.1~5.3 已完成宠物数据模型、SQLite 持久化、Pixi.js 动画系统与行为状态机。
当前主窗口（`main`，300×300 透明无边框）仅作为"宠物舞台"渲染一只写死的占位宠物
（`PLACEHOLDER_PET_ID`），未与数据库联动。

阶段 5.4 目标：实现宠物管理 UI（创建/列表/详情/设置四个界面），并打通管理操作
到桌面舞台的端到端联动——管理窗口的增删改实时反映到舞台精灵，舞台启动时从数据库
加载真实宠物，替换占位逻辑。

---

## 2. 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 管理界面承载方式 | **独立管理窗口** | 舞台窗口透明/小尺寸不适合放表单列表；两窗口单一职责解耦；符合桌宠应用惯例；后续 AI/P2P 设置可复用 |
| 舞台与数据库联动 | **端到端打通** | 管理操作真实反映到桌面，是本阶段最有价值产出；顺势清理占位代码 |
| 四界面布局 | **左列表 + 右详情主从布局** | 信息密度高，列表/详情同屏切换流畅；新建/设置用 Modal 避免跳转 |
| 设置可编辑范围 | **仅名称 + 性格** | 类型创建后不可改（避免形象错乱）；等级/经验是成长产物；状态由行为系统驱动；只暴露真正属于用户偏好的字段（YAGNI） |

---

## 3. 架构概览

```
┌─ main 窗口 (300×300 透明) ─┐      ┌─ manager 窗口 (800×600 常规) ─┐
│   Pixi 宠物舞台            │◄────►│  React 管理 UI (主从布局)      │
│   渲染真实宠物精灵          │ event │  列表 + 详情 + Modal(新建/设置)│
└───────────────────────────┘      └───────────────────────────────┘
        ▲                                      │
        │  get_pets / create_pet / delete_pet  │
        └──────────── SQLite (已有命令) ◄───────┘
```

- 两窗口共用同一前端打包，按 URL query（`?window=manager`）区分入口。
- 跨窗口同步通过 Tauri event（`pets-changed`）广播。
- 打开入口：托盘菜单新增"管理宠物"项（右键宠物菜单可选，本阶段先做托盘）。

## 4. 组件划分

### 4.1 后端（Rust）

- `window/mod.rs`：新增 `open_manager_window(app)`，用 `WebviewWindowBuilder` 创建/聚焦
  `manager` 窗口。已存在则 `set_focus`，避免重复创建。托盘菜单新增 `MENU_ID_MANAGE` 项。
- `commands/mod.rs`：
  - 复用 `get_pets / create_pet / delete_pet / get_pet_state`
  - 新增 `update_pet`（改名称 + 性格，含名称校验，复用 `PET_NAME_MAX_LEN`）
  - 新增 `open_manager`（前端可调用打开管理窗口）
  - 增删改成功后 `app.emit("pets-changed", payload)` 广播

### 4.2 前端（React）

- `src/manager/ManagerApp.tsx`：主从布局容器，持有宠物列表与选中态
- `src/manager/PetList.tsx`：左栏列表（选中高亮、新建按钮、空态引导）
- `src/manager/PetDetail.tsx`：右栏详情（属性 + 心情/能量进度条 + 设置/删除按钮）
- `src/manager/PetFormModal.tsx`：新建/编辑共用表单 Modal（名称 + 类型[仅新建] + 性格）
- `src/services/pet-api.ts`：封装所有 `invoke` 调用，管理 UI 与舞台共用（DRY）

### 4.3 舞台联动（App.tsx 改造）

- 启动时 `getPets()` 加载，为每只宠物 `engine.addPet`，移除 `PLACEHOLDER_PET_ID` 占位逻辑
- 监听 `pets-changed`，增量 `addPet` / `removePet` / 更新同步精灵

### 4.4 入口分流（main.tsx）

读 `window.location.search`：`manager` 渲染 `ManagerApp`，否则渲染舞台 `App`。

## 5. 数据流

### 创建
```
Modal 填写 → pet-api.createPet(NewPet)
  → invoke('create_pet') → DB 写入 + 初始化默认状态 → 返回 Pet(含id)
  → emit('pets-changed', {kind:'created', pet})
  → manager: 刷新列表、选中新宠物、关闭 Modal
  → main: engine.addPet(pet.id, {personality, color})
```

### 删除
`deletePet(id)` → 软删除 → emit `{kind:'deleted', id}`
→ manager 列表移除并清空详情；main `engine.removePet(id)`。
删除前 Modal 二次确认（破坏性操作）。

### 编辑
`updatePet({id,name,personality})` → emit `{kind:'updated', pet}`
→ manager 刷新详情；main 若性格变化则更新行为（本阶段可仅刷新，性格热更新可选）。

### 详情状态读取
选中宠物时 `getPetState(id)` 拉取心情/能量/动作渲染进度条。
状态为实时运行值，本阶段只读展示，不轮询（YAGNI）。

## 6. 错误处理

- 所有 `invoke` 在 `pet-api.ts` 统一 `try/catch`，向 UI 抛友好中文错误
  （如"宠物名称不能为空"直接来自后端校验）
- Modal 表单前端预校验（名称非空、≤50 字符）与后端对齐，双重保险
- 空列表显示引导态（"还没有宠物，点击新建"）
- `emit` 失败不阻塞主流程，仅记录日志（最坏两窗口短暂不同步，下次打开自动一致）

## 8. 范围边界（不做）

- 形象资源选择（avatar_path）：当前为程序化占位精灵，真实美术资源接入后再做
- 等级/经验手动编辑：成长系统产物，不暴露
- 宠物状态轮询刷新：本阶段只读快照
- 右键宠物菜单打开管理窗口：本阶段先做托盘入口
- 多窗口复杂状态管理：本阶段两窗口 + event 足够
